* Overview
:PROPERTIES:
:CUSTOM_ID: overview
:END:

~mailx~ is an extensible, transport-independent mail management suite for GNU Emacs
and [[https://www.djcbsoftware.nl/code/mu/mu4e.html][mu4e]].  It provides declarative S-expression classification rules, a three-stage
cascading classifier, multi-tier attention bookmarks, reviewable bulk triage via
[[https://github.com/tychoish/hitl][hitl-plan]], context-aware Org mode links, and Model Context Protocol (MCP) inspection
tools.

** Key Features
:PROPERTIES:
:CUSTOM_ID: key-features
:END:

- *Declarative Rules DSL*: Express routing and attention policies with composable S-expressions (~:and~, ~:or~, ~:not~, ~:from~, ~:to~, ~:list~, ~:subject~, ~:has-unsubscribe~).
- *Delivery Exporters & Importers*: Export portable rule sets to [[https://github.com/nicm/fdm][fdm]] configuration or [[https://en.wikipedia.org/wiki/Procmail][procmail]] recipes, and import legacy procmail filter directories.
- *Three-Stage Classification Cascade*: Deterministic rule matching and correspondent caching in stage 1, receipt and transactional heuristics in stage 2, and optional LLM classification in stage 3.
- *Attention-Oriented Views*: Five attention tiers (~reply~, ~read~, ~cursory~, ~bulk~, ~junk~) with dynamic unread count annotations and custom headers columns.
- *Reviewable Bulk Triage*: Stage and execute batch mail operations (~mark-read~, ~refile~, ~tag~, ~unsubscribe~, ~block-sender~, ~expire-older~) using Human-in-the-Loop plans.
- *Context-Aware Org Integration*: Context-qualified ~mailx:~ link types that switch database contexts automatically before jumping to messages.
- *MCP Service*: Headless inspection tools (~list_unclassified~, ~test_rule~, ~add_rule~, ~stage_triage_plan~) guarded by path allowlists.  ~add_rule~ only stages a one-step hitl plan (op ~promote-rule~) for human review and returns the plan id; set ~mailx-mcp-direct-rule-writes~ to non-nil to persist and export immediately.

* Configuration
:PROPERTIES:
:CUSTOM_ID: configuration
:END:

Initialize ~mailx~ in your Emacs configuration with `mailx-global-mode`:

#+begin_src emacs-lisp
(use-package mailx
  :commands (mailx-global-mode mailx-setup mailx-make-context)
  :init
  (mailx-global-mode 1)
  :config
  (setq mailx-default-maildir "~/mail"
        mailx-archive-folder "/archive")

  ;; Optional: customize managed settings applied when mode is active
  ;; (setq mailx-global-managed-settings '(...))

  ;; Optional: configure account contexts
  (setq mu4e-contexts
        (list
         (mailx-make-context
          :name "personal"
          :full-name "Your Name"
          :address "you@example.com"
          :maildir "~/mail"
          :command "mbsync personal"))))
#+end_src

* Workflows & Examples
:PROPERTIES:

** Interactive Refile Rule Generation
:PROPERTIES:
:CUSTOM_ID: workflow-refile-rules
:END:

While viewing or navigating headers in mu4e, invoke ~M-x mailx-generate-refile-rule~.  You will be prompted to select a message field, specify a regular expression, choose a destination folder, and assign an attention tier.  Before saving, a live preview matches against the active database and reports matching counts. 

** Attention Tier Navigation
:PROPERTIES:
:CUSTOM_ID: workflow-attention-tiers
:END:

Invoke ~M-x mailx-jump-to-tier~ to choose from the five tiers.  Each option displays real-time unread counts:
- *reply*: High-attention messages requiring personal responses.
- *read*: Substantive threads to read with lower immediacy.
- *cursory*: Informational messages, newsletters, notifications.
- *bulk*: High-volume automated communications.
- *junk*: Unsolicited messages and spam.

** Bulk Triage Plans
:PROPERTIES:
:CUSTOM_ID: workflow-bulk-triage
:END:

From a headers buffer, run ~M-x mailx-bulk-stage-current-view~ to snapshot the visible messages into a reviewable plan.  Inside the review interface, queue actions (~r~ for mark read, ~m~ for refile, ~b~ to block sender and trash) before committing them atomically.

** Reviewing Proposed Classifications
:PROPERTIES:
:CUSTOM_ID: workflow-review
:END:

Run ~M-x mailx-review~, or pick /review classifications/ from the mu4e actions menu (~a~ in a headers or message view), to classify unclassified mail without changing it.  From a headers buffer, /stage view as plan/ in the same menu runs ~mailx-bulk-stage-current-view~.  Press ~?~ in the review buffer for its keys.  Each proposal appears in a table with its tier, folder, tags and source (a named rule, a heuristic, or ~none~ when no stage could classify the message).  Nothing is moved from this buffer.

| Key | Action |
|---|---|
| ~a~ / ~s~ | Accept / skip the entry at point (or every entry in the region) and move on. |
| ~*~ | Accept every pending entry that already has a tier and folder. |
| ~t~ / ~f~ / ~l~ | Set the tier, folder or tags of the entry at point (or region). |
| ~r~ | Save a rule reproducing the entry.  It matches the message's mailing list when it has one, the exact sender address for a domain in ~mailx-freemail-domains~ (gmail.com and similar), else the sender's whole domain; ~C-u r~ lets you choose address, domain or list.  The confirmation shows the match count and, when an earlier rule already matches this message (first match wins), which rule shadows the new one.  Existing rules are never reordered; press ~g~ afterwards to reclassify the other entries. |
| ~x~ | Turn accepted entries into a ~mailx~ hitl plan and open it for review. |
| ~o~ | Reopen the hitl plan holding the planned entry at point (its id is also messaged when you press ~x~). |
| ~v~ | View the raw message file. |
| ~g~ | Reclassify (asks first if that would discard decisions). |

Exclusive Maildir access is asserted only when the hitl plan is applied, so stop mail delivery and sync clients before applying it.  With a running mu4e server for the root, applying goes through it and keeps the index current; otherwise files are moved directly and applying reminds you to run ~mu4e-update-index~ and press ~g~.  Messages whose files have disappeared (a stale index) are dropped on load, counted in the mode line as ~[N stale]~.

Set ~mailx-sent-query~ to a mu query matching mail you sent.  Batch classification then keeps the correspondent cache fresh (see ~mailx-correspondents-max-age-days~) so mail from people you write to is proposed as ~reply~.  Without it, the cache is not refreshed and the review mode line shows ~[no sent query]~ and a message names the variable; a failed refresh shows ~[correspondents failed]~ with the error.  When the batch hit ~mailx-review-limit~ the mode line shows ~[first N]~: more messages may remain, so raise the limit or press ~g~ after applying.  Oldest mail comes first, since ~mu find~ sorts by date ascending unless told otherwise.

** Classification Rules
:PROPERTIES:
:CUSTOM_ID: classification-rules
:END:

Rules are stored per mail root in ~tools/mailx-rules.eld~ (see ~mailx-rules-filename~; the path is ~<root>/tools/mailx-rules.eld~ by default).  The file holds one Lisp list of property lists, read with ~read~, and it is safe to edit by hand.  A file that fails to load is reported with its path, the entry index and the rule id; duplicate ids and data after the list are rejected.

#+begin_src emacs-lisp
((:id example-news :match (:and (:from "news@example\\.com") (:has-unsubscribe))
  :folder "/archive" :tier cursory :tags ("newsletter")
  :expire-days 30 :source manual :created "2026-11-23"))
#+end_src

| Field | Meaning |
|---|---|
| ~:id~ | Unique symbol naming the rule. |
| ~:match~ | Condition, see below. |
| ~:folder~ | Destination maildir, must start with ~/~ and contain no ~..~; ~nil~ keeps the message where it is. |
| ~:tier~ | One of ~reply~, ~read~, ~cursory~, ~bulk~, ~junk~, or ~nil~. |
| ~:tags~ | List of strings without whitespace, control characters or commas. |
| ~:expire-days~ | Optional positive integer retention hint stored with the rule; mailx does not act on it. |
| ~:source~ | Provenance symbol (~manual~, ~imported~, ~mcp~, ...). |
| ~:created~ | Creation date string. |

Conditions are lists whose first element is an operator.  Patterns are Emacs regular expressions, matched case-insensitively against the message fields; address fields are searched by both display name and address.

| Operator | Matches |
|---|---|
| ~(:from RE)~ | The From header. |
| ~(:to RE)~ | The To or Cc headers. |
| ~(:delivered-to RE)~ | The Delivered-To or X-Forwarded-To headers. |
| ~(:list RE)~ | The mailing list id. |
| ~(:subject RE)~ | The subject. |
| ~(:maildir RE)~ | The message's current maildir, for example ~/inbox~. |
| ~(:tag STRING)~ | A tag equal to STRING (exact, case-sensitive; not a regexp). |
| ~(:has-unsubscribe)~ | The message has a List-Id or List-Unsubscribe header. |
| ~(:and C...)~, ~(:or C...)~, ~(:not C)~ | Boolean combinations; ~:and~ and ~:or~ need at least one operand and ~:not~ exactly one. |

*The first matching rule wins*, in file order.  A broad rule above a specific one shadows it: with ~(:from "example")~ to ~junk~ listed before ~(:from "boss@example")~ to ~reply~, mail from ~boss@example.com~ is classified ~junk~ and the second rule never fires.  Keep specific rules first.

Emacs cannot interrupt a regexp match, so a pattern with a quantified group that contains a quantifier, such as ~\(a*\)*b~, can freeze Emacs.  New rules containing that shape are rejected and existing ones produce a warning when loaded.  This is a heuristic, not a guarantee.

Rules also drive delivery-time filters.  ~mailx-rules-export-all~ writes ~tools/mailx-generated.procmailrc~ and ~tools/fdm.conf~ beside the rules file; do not edit those by hand.  Conditions a delivery agent cannot evaluate (~:maildir~, ~:tag~, and ~:or~ for procmail) are skipped for that target and reported under ~:skipped~ in the result.  In the review buffer, ~r~ promotes the entry at point to a new rule (see above), which is appended after existing rules and therefore never shadows them, but may itself be shadowed.
